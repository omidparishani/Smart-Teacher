# Mini App — راهنمای توسعه

> برنامک ایتا برای معلم · React 19 + TypeScript + Vite
> معماری کامل: [`../docs/mini-app.md`](../docs/mini-app.md)

---

## راه‌اندازی

```bash
npm ci
npm run dev        # http://localhost:5173
```

> ⚠️ **بیرون از ایتا، برنامه صفحه «این برنامه باید از داخل ایتا باز شود» را نشان
> می‌دهد.** این رفتار درست است، نه خطا.

برای کار روی دستگاه توسعه:

۱. یک `initData` جعلی بگیرید (از بک‌اند در پروفایل `dev`).
۲. آن را در **`.env.development.local`** بگذارید:

```dotenv
VITE_DEV_INIT_DATA=<initData جعلی>
```

> 🔴 **این فایل `.env.development.local` است، نه `.env.local`.**
> Vite فایل `.env.local` را در **همه** حالت‌ها می‌خواند — از جمله `vite build`. یعنی
> هر مقدار «فقط توسعه» که آنجا بگذارید به باندل محصول راه پیدا می‌کند.
> تفاوت این دو نام، یک جزئیات سلیقه‌ای نیست. اگر اشتباه بگذارید، بیلد در ترمینال
> هشدار می‌دهد ولی **متوقف نمی‌شود** (چون مقدار واقعاً به باندل نمی‌رسد — بخش
> «دروازه تولید» پایین‌تر).

۳. بک‌اند را با `app.mock.eitaa=true` بالا بیاورید:

```bash
cd ../backend && mvn spring-boot:run -Dspring-boot.run.profiles=dev
```

## دروازه کیفیت

هر پنج مورد باید سبز باشند پیش از اینکه تغییری «تمام‌شده» حساب شود:

```bash
npm run typecheck     # tsc -b — هر سه پروژه TypeScript
npm run build         # tsc -b + vite build + verify-bundle
npm run test          # Vitest — آزمون‌های واحد و کامپوننت
npm run e2e           # Playwright — مرورگر واقعی
npm run lint          # ESLint
npm run size-check    # بودجه باندل — ۱۵۰ kB gzip
```

| سنجه | مقدار فعلی | سقف |
|---|---|---|
| باندل اولیه | ۱۳۱.۲۵ kB gzip | ۱۵۰ kB |
| تست واحد | ۱۵۶ تست · ۱۳ فایل | — |
| تست E2E | ۱۷ تست | — |
| خطای ESLint | ۰ | ۰ |

> ⚠️ **`npm run e2e` به Chrome نصب‌شده روی سیستم وصل می‌شود** (`channel: 'chrome'`).
> دانلود خودکار Chromium روی شبکه‌های با پروکسی TLS بازدارنده شکست می‌خورد
> (`UNABLE_TO_VERIFY_LEAF_SIGNATURE`). روی ماشینی که Chrome ندارد، این آزمون‌ها اجرا
> نمی‌شوند. جزئیات و هزینه‌اش: `docs/verification-log.md` بخش ۱۲.۵.

## 🔴 دروازه تولید — `VITE_DEV_INIT_DATA`

مقدار توسعه **نباید** به باندل Production برسد. این تضمین دو تکه دارد:

**۱. ترتیب شرط‌ها در `src/eitaa/init-data.ts`.** شرط `import.meta.env.PROD` **اول**
می‌آید:

```typescript
if (import.meta.env.PROD) {
  // مسیر تولید — شاخه توسعه زیر این خط هرگز در باندل نمی‌ماند
  ...
}
const devData = import.meta.env.VITE_DEV_INIT_DATA;
```

چون Vite در بیلد این را به `true` تبدیل می‌کند، **bundler کل شاخه توسعه را به‌عنوان
کد مرده حذف می‌کند** — نه فقط مقدار را. این اندازه‌گیری شده است، نه استنباط
(`docs/verification-log.md` بخش ۱۲.۲).

> 🔴 **اگر این ترتیب را عوض کنید، دروازه باز می‌شود.** ترتیب، یک سلیقه‌ی کدنویسی نیست؛
> خودِ کنترل امنیتی است.

**۲. `scripts/verify-bundle.mjs`.** در زنجیره `npm run build` اجرا می‌شود و باندل
نهایی را می‌خواند. اگر مقدار ممنوعی را ببیند، **بیلد را با شکست متوقف می‌کند**.

> ⚠️ این اسکریپت خودش با یک «قناری» آزموده شده: یک مقدار ساختگی در فایل محیطی و در
> باندل کاشته شد و دروازه شکست خورد. دروازه‌ای که هرگز شکست نخورده، معلوم نیست کار
> می‌کند یا نه.

## کجا چه‌کاری کنم؟

| پرسش | پاسخ |
|---|---|
| این Component چیست؟ | JSDoc بالای فایل |
| این فایل چه کاری می‌کند؟ | JSDoc بالای فایل |
| API کجاست؟ | `src/features/<name>/api.ts` · کلاینت پایه: `src/lib/api-client.ts` |
| State کجا مدیریت می‌شود؟ | سرور: TanStack Query · کاربر/نشست: `src/stores/auth.store.ts` |
| تم و تنظیمات UI؟ | `src/stores/ui.store.ts` |
| UI را کجا تغییر دهم؟ | `src/features/<name>/` |
| API تغییر کرد، کجا عوض کنم؟ | `src/lib/api-client.ts` یا `src/features/<name>/api.ts` — **نه کامپوننت‌ها** |
| رنگ یا فونت را کجا عوض کنم؟ | `src/index.css` (بلوک `@theme`) |
| یک تب جدید اضافه کنم؟ | `src/components/layout/TabBar.tsx` + `src/router/navigation.ts` |
| SDK ایتا را عوض کنم؟ | `src/eitaa/` — **فقط همین‌جا.** هیچ کامپوننتی مستقیم با SDK حرف نمی‌زند |

## 🔴 قواعد سرسخت

این‌ها قابل مذاکره نیستند. هر کدام یک دلیل مشخص دارد.

**۱. هیچ کامپوننتی مستقیماً با SDK ایتا حرف نمی‌زند.**
همه از `src/eitaa/sdk.ts` عبور می‌کنند. اگر ایتا نامی را عوض کند، **یک فایل** اصلاح
می‌شود.

**۲. Access Token فقط در حافظه می‌ماند؛ Refresh Token در `localStorage`.**
Access Token عمداً persist نمی‌شود (Zustand، بدون `persist`). Refresh Token **باید**
بمـاند، وگرنه با هر پس‌زمینه‌شدن WebView اپ ناچار است با `initData` وارد شود — و آن
یک‌بارمصرف و ۵دقیقه‌معتبر است، پس رد می‌شود و کاربر در حلقه «دوباره تلاش کنین»
گیر می‌کند. ریسک XSS باقی‌مانده با چرخش توکن، تشخیص استفاده مجدد خانوادگی و خروج
مهار شده است. جزئیات: `src/lib/token-storage.ts`

**۳. `start_param` داده غیرقابل‌اعتماد است.**
فقط الگوی `type_<عدد>` پذیرفته می‌شود (`asg_`, `cls_`, `exm_`). هر مقدار دیگری نادیده
گرفته می‌شود. بک‌اند **مستقل** بررسی می‌کند که آن منبع به مستأجر جاری تعلق دارد.

**۴. هر متد SDK فقط با Feature Detection صدا زده می‌شود.**
`eitaa.atLeast('1.3')` — و اگر موجود نبود، **Fallback خودمان** اجرا می‌شود، نه اینکه به
وجود آن تکیه کنیم.

**۵. گارد پلتفرم پیش از هر تماس شبکه‌ای اجرا می‌شود.**
کاربر iOS نباید اول یک درخواست ورود بفرستد و بعد پیام «پشتیبانی نمی‌شود» ببیند.

**۶. `axe` باید گزارش خالی بدهد.**
نه «بدون مورد جدی». هر صفحه در **دو تم** اسکن می‌شود (بخش ۱۲.۱ `docs/mini-app.md`).

## ساختار

```
src/
├── eitaa/       ← تنها نقطه تماس با SDK ایتا
├── lib/         ← api-client، auth-api، token-storage، platform-guard
├── stores/      ← auth.store · ui.store (Zustand)
├── router/      ← routes · start-param · navigation
├── components/  ← layout · shared
├── features/    ← یک پوشه برای هر قابلیت
└── types/       ← api.ts · error-codes.ts
e2e/             ← آزمون‌های Playwright (SDK و بک‌اند جایگزین می‌شوند)
scripts/         ← verify-bundle.mjs
```

## آزمون‌ها

| پوشه | نوع | ابزار |
|---|---|---|
| `src/**/*.test.ts(x)` | واحد و کامپوننت | Vitest + Testing Library (jsdom) |
| `e2e/*.spec.ts` | E2E و دسترس‌پذیری | Playwright + axe-core |

**دو جایگزین (Mock) در E2E:**
`e2e/support/eitaa.ts` هم `window.Eitaa.WebApp` را جعل می‌کند و هم `**/api/v1/**` را
مسدود و پاسخ‌دهی می‌کند. پس آزمون نه به شبکه وابسته است و نه به بالا بودن سرور.

> ⚠️ **و همین یعنی آزمون‌های E2E قرارداد را می‌سنجند، نه سرور واقعی را.** «ورود با
> یک نشست واقعی ایتا» همچنان آزموده نشده است.
